## 已知环境问题（与代码无关）

在本机当前会话中，**任何 eframe/egui 程序都只显示白屏**（只有一个标题栏），
包括不带任何自定义 UI 的最小示例 `cargo run --example mini_ui`。

判定依据：
- 最小示例也白屏 → 排除业务代码；
- 软件渲染（`LIBGL_ALWAYS_SOFTWARE=1`）同样白屏 → 排除显卡驱动差异；
- 程序无 stderr 输出、进程正常存活 → 不是崩溃；
- Win32 UI 树中窗口存在且尺寸正常，但内部没有任何控件 → egui 未产出绘制内容。

此前同一台机器、同一份代码曾正常渲染并完成过完整交互验证（框选、实体管理、
危险操作确认、占用保护提示），因此这是**会话/环境层面的状态异常**，建议：
1. 重启该程序；若无效，注销或重启一次 Windows 会话；
2. 更新显卡驱动；
3. 若仍复现，可尝试把 `eframe` 换成 `wgpu` 后端（需可用的 C 工具链，见下）。

## 构建

本机没有 MSVC 构建工具、也没有 MinGW gcc，且 DSH 沙箱隔离了系统 `%TEMP%`。
`build.cmd` 已把这些约束固化：

```cmd
build.cmd                       :: 构建
build.cmd test -p mcworld-core  :: 跑测试
build.cmd run -p mcworld-app    :: 运行 GUI
```

产物：`target\x86_64-pc-windows-gnullvm\debug\mcworld-app.exe`

### 工具链要点

- **目标** `x86_64-pc-windows-gnullvm`：std 自包含，不依赖 dlltool；
- **链接器** 用 rust 自带的 `rust-lld`（`ld.lld` 驱动），flag 写在 `.cargo/config.toml`；
- **host** 用 `stable-x86_64-pc-windows-gnu`：proc-macro 必须按 host 编译，
  而 gnu host 下 `windows-link` 会触发 `raw-dylib` → 调用 Cygwin dlltool，
  该程序在沙箱里起不来。**所以不要清理 `target/`**，否则 proc-macro 需要重编就会失败；
- **release 构建当前不可用**，原因同上（release 会为 proc-macro 单独编一份）。
  已把 `[profile.dev]` 提到 `opt-level = 1` 作为替代。

## 第四轮：三个体验问题（2026-10-31）

### 1. 启动不再弹出命令窗口

以 PE 的 **GUI 子系统**链接（`Subsystem = 2`），双击 exe 不再出现黑色控制台。

实现方式（两处配合，因为 `windows_subsystem` 属性只对非 debug 生效）：

- `main.rs` 顶部加 `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`
- `.cargo/config.toml` 的 rustflags 里加 `-C link-arg=--subsystem -C link-arg=windows`
  （注意：在 `ld.lld` 驱动下不能用 gcc 风格的 `-Wl,--subsystem,windows`，否则报
  `lld: error: unknown argument`）

验证：读 PE 头偏移 `+0x5C` 得 `Subsystem = 2 (GUI)`。

### 2. 下界顶部基岩不再遮挡地形

下界在 Y=127 附近有一到两层基岩天花板。原先的地表采样取"最顶层非空气方块"，
于是整个下界被渲染成一片基岩灰。

现在采样时会**穿透基岩**继续向下找真正的地表：

```rust
// colors.rs
pub fn is_cover_block(name: &str) -> bool {
    matches!(name.strip_prefix("minecraft:").unwrap_or(name), "bedrock")
}
```

顺带修正：主世界底部那种"整列只有基岩"的情况会正确变成空列（而不是显示成地表）。

测试：`surface_skips_bedrock_ceiling`、`surface_all_bedrock_column_becomes_empty`。

### 3. 切换维度不再丢失地形（重构）

**根因**：`map`（区块纹理）、`camera`、`selection`、`regions`、`chunk_entity_types`
原来都是 `WorldTab` 上的**单份**字段，切换维度时被 `clear()` 掉，
而且 `request_scan` 发现该维度已扫描过就直接返回，采样永远不会重新触发。

**修复**：引入按维度隔离的视图状态。

```rust
pub struct DimView {
    pub map: TileCache,          // 区块纹理
    pub camera: MapCamera,       // 相机（位置/缩放）
    pub selection: Option<ChunkSelection>,
    pub regions: Vec<Region>,
    pub chunk_entity_types: HashMap<(i32,i32), Vec<(String,usize)>>,
    pub sampled: bool,
}

pub struct WorldTab {
    // ...
    pub views: HashMap<String, DimView>,   // 维度 id → 视图状态
}
```

- 切换维度现在只改 `current_dim`，**不碰任何已加载数据**；
- 切走再切回是瞬时恢复，不需要重新扫描或采样；
- 采样结果根据任务返回的 `dimension` 写进对应维度，即使中途切到别的维度也不会写错；
- 只有显式「写操作后刷新」或关闭存档才会重建视图。

实测：主世界 → 下界 → 主世界 → 下界，两端地图都原样保留。

### 2. 可自定义渲染高度

地图工具栏新增「渲染高度」：

```
渲染高度  [默认 (Y65)]  [自定义]  Y 64  [应用]
```

- 默认：主世界用"地表"，下界用 Y65
- 自定义：拖动或用键盘输入 Y（范围 -64..319），点「应用」重新采样

### 3. 鼠标悬停显示坐标 / 区块 / 群系

```
X 130  Z -74   |   区块 (8, -5)   |   stone @ Y-20   |   群系 crimson_forest
```

## 备份机制（2026-10-31 建立）

### 规则

**每次修改源码前，先备份一次。**

### 用法

```bat
backup.cmd "本次要做什么"
```

或

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File backup.ps1 -Desc "本次要做什么"
```

### 产出

全部放在 `存档管理器工程备份\` 下：

| 文件 | 说明 |
|---|---|
| `backup_<时间戳>_<描述>.zip` | 源码压缩包（含目录结构） |
| `备份记录.md` | 追加式表格，记录时间 / 操作 / 文件名 / 文件数 / 大小 |

### 备份内容

- `crates/`（全部源码、示例、资源）
- `docs/`
- `.cargo/`
- `Cargo.toml` / `Cargo.lock`
- `build.cmd` / `backup.ps1` / `backup.cmd`

**不备份**：`target/`（4.4 GB 构建产物）、`.toolchain/`、`.build/`、`发布/`。

### 实现要点

- `backup.ps1` **必须保持纯 ASCII**。Windows PowerShell 5.1 按系统 ANSI 代码页
  读取 `.ps1`，脚本里写中文会导致解析失败（`Unexpected token`）。
  目录名等中文文本在运行时用码点拼装（`U {5B58,6863,...}`）。
- 用 `System.IO.Compression.ZipFile` 压缩，条目路径相对工程根目录。
- 日志用 UTF-8 with BOM 写入，保证记事本正确显示中文。

### 已验证

- 备份 34 个源码文件，169 KB
- 解压后与源码逐个比对 SHA256：**34 个完全一致，0 差异 0 缺失**

## 第七轮：程序图标 + 26.3 版本适配（2026-10-31）

### 1. 程序图标

源图 `crates/app/assets/icon_source.jpg`（1536×1536 蓝色文件夹）。

**exe 文件图标**（资源管理器 / 任务栏）：

```
icon_source.jpg
  → icon.ico       7 种尺寸 (16/24/32/48/64/128/256)，PNG 压缩条目
  → icon_obj.obj   COFF 对象，含 .rsrc 节
  → 链接参数       -C link-arg=crates/app/assets/icon_obj.obj
```

**为什么绕这么大圈**：`ld.lld` 不支持 MSVC 的 `--icon=`，也不认识 `.res` 文件

> 踩坑：PE 资源目录项的 Name 字段是 **DWORD**（bit31 = 字符串名标志），
> 不是 WORD。写成 WORD 会导致类型 ID 变成 32771 这种离谱值。

**窗口图标**：`icon_source.jpg → icon_32.rgba`（原始 RGBA），
由 `main.rs` 的 `window_icon()` 用 `include_bytes!` 内嵌。

验证：`[System.Drawing.Icon]::ExtractAssociatedIcon(exe)` 成功返回 32×32 图标。

## 第八轮：修复 26.x 地图灰块 / 黑块（2026-10-31）

参考工程：`D:\工程-迅捷地图`（只读，未修改）。

### 问题现象

26.3 存档地图出现大片灰色和黑色方块，1.21.1 正常。

### 根因（两个，叠加）

#### 1. 地表判定语义错误（主因）

原实现：`从顶层向下取第一个非空气方块`。

这在三种情况下会错：

| 场景 | 原逻辑 | 正确语义 |
|---|---|---|
| 洞穴顶部 | 停在被岩层封住的实心块上 | 只有**上方紧邻空气**的才算地表 |
| 树冠 | 停在树下地面 | 命中树冠（叶子上方是空气） |
| 下界顶盖 | 停在顶盖 | 继续往下找真正的岩面 |

修正（参考 SwiftMap `ClientChunkCapture`）：

```
"地表" = 上方紧邻空气的非空气方块
```

关键细节：**扫描起点之上按"非空气"处理**，否则整列最顶上那层永远不会被命中。
逐列维护 `above[col]` 状态，整段空气的 section 把所有列标记为"上方是空气"。

#### 2. 区块没生成完（真正的视觉原因）

**这个 26.3 存档里 68% 的区块根本没生成完**：

| Status | 数量 | 含义 |
|---|---|---|
| `structure_starts` | 1376 | 只放了结构，**地形还没生成** |
| `full` | 841 | 完整 |
| `biomes` | 136 | 只有群系 |
| `terrain` | 128 | 只有地形，没有表面装饰 |
| `initialize_light` | 120 | 光照阶段 |

这些阶段的区块**没有草、植被、水面**，只有裸石/深板岩。所以渲染成灰色是**正确的**。

处理方式：`ChunkSurface` 新增 `complete: bool`，未完成的区块在地图上**压暗 35%**，
并在工具栏下方显示提示条：

```

  游戏在这些地方只生成了基础地层，还没有草、植被和水
```

### 顺带的视觉改进

1. **坐标微扰**：同一方块在不同位置有 ±4 的亮度差（基于坐标哈希，确定性不会闪烁），
   大面积同色地形（成片的石头/沙/雪）才有层次感，不再是一整块死色。

## 第九轮：真正的 26.x 渲染 bug 修复（2026-10-31）

用户指出「那不是没有加载，就是渲染错误」——**完全正确**。
我上一轮把灰块归因于「区块没生成完」是错的，真正的 bug 在调色板解析。

### 根因：26.x 的调色板项键名是空字符串

26.3 的 `block_states.palette` 项是复合物，但键名是 **`""`** 而不是 `"Name"`：

```nbt
Compound({ "": String("minecraft:deepslate") })
```

原实现只查 `Name` / `id` 两个键，查不到就返回 `"minecraft:air"`。
结果：**每个 section 的调色板几乎全被读成空气**，地图出现大片空列（黑块）

|---|---|---|
| 有方块列 | 37 / 256 | **256 / 256** |
| 地表方块 | `andesite` / `deepslate`（错） | **`grass_block` / `sand` / `water`（对）** |

### 修复

`read_palette` 重写为 `palette_entry_name`，按顺序尝试四种形式：

1. 裸字符串 `"minecraft:stone"`
2. `{Name: "minecraft:stone", Properties: {...}}` — 1.16–1.21.1
3. `{id: ...}` / `{name: ...}` — 部分工具
4. **`{"": "minecraft:stone"}` — 26.x 实测**
5. 兜底：取复合物里第一个字符串值

### 顺带修正

- **下界默认也改用 Surface**（原来用固定 `Y=65`）。

- **去掉「未生成」误报提示**：原提示把 `structure_starts` 也算作未生成，

## 第十一轮：重新设计程序图标（2026-10-31）

### 设计思路

原来用的是用户提供的蓝色文件夹图标，与「Minecraft 存档管理器」的功能不够贴合。
新图标围绕程序特点设计：

`.build/icon_gen.cs` 用 GDI+ 在 1024×1024 上矢量绘制，再交给现有工具链：

```
  ├→ dump_rgba.exe      → icon_64.rgba  原始 RGBA（窗口图标）
  │    └→ main.rs window_icon() 用 include_bytes! 内嵌
```

窗口图标从 32×32 升级到 **64×64**，高 DPI 下更清晰。

### 工具链说明（踩坑记录）

- `ld.lld` 不支持 `--icon=`，也不认 `.res` 文件 → 必须自己生成带 `.rsrc` 节的 COFF 对象
- PE 资源目录项 Name 字段是 **DWORD**（bit31 为字符串名标志），写成 WORD 会让类型 ID 变成 32771
- `.obj` 不在 cargo 的依赖追踪里 → 换图标后要 touch 一下 `main.rs` 才会重新链接
- C# 5（.NET Framework 自带 csc）不支持表达式体方法 `=>`，要写完整方法体

## 第十三轮：接入 SwiftMap 小地图数据（2026-10-31）

参考 `D:\工程-迅捷地图`（SwiftMap 模组）的格式规范，实现了只读解析，
让存档管理器能直接复用该模组已经采集好的地图颜色，省去全量扫描。

### 为什么只读

SwiftMap 的 `.smr` 容器里有 **CRC32C 校验**和**双索引代际提交**机制
（先写数据 → 再写索引副本 → 最后改 header 作为提交点）。
第三方写入极易破坏这个不变量，所以这里**只读不写**。

### 实现的格式（`crates/core/src/swiftmap.rs`）

**目录**
```
<存档>/swiftmap/
  identity.json
  dimensions/<namespace>/<path>/
    format.json
    lod0/r.<cx>.<cz>.smr        ← 颜色瓦片容器
    structures.jsonl
```

**.smr 容器**
```
0x00  header        64 B   magic="SMR1", version, genA, genB, appendOffset, slotCount, lod
0x40  index copy A  slotCount × 32 B
0x840 index copy B  slotCount × 32 B
0x1040 data area    只追加
```

生效的索引是**代际更大**的那份副本（header 的提交点语义）。

**槽位（32 B）**：`state / flags / offset / storedLen / rawLen / crcStored / contentHash / childGen / writeSeq`

**瓦片负载（大端）**
```
short paletteSize
int[paletteSize] palette     0xRRGGBB
byte[4096] indices           索引 0 = 无数据
short[4096] heights          （可选）
short biomeCount + 群系段     （可选）
```

**几何关系**（必须用 floorDiv / floorMod，负数象限才不跑偏）
```
1 格 = 1 像素（LOD0）    1 区块 = 16×16 格
1 瓦片 = 64×64 格 = 4×4 区块
1 容器 = 8×8 瓦片 = 32×32 区块 = 512×512 格 = 64 槽位
槽位号 = (tileZ & 7) * 8 + (tileX & 7)
```

支持压缩：`flags` 的 bit0 表示已压缩，bit1..3 是 codec id（0=不压缩，1=Deflate）。

### 接入

- `WorldTab::swiftmap` 在打开存档时自动探测 `<存档>/swiftmap/dimensions`
- 侧栏新增「SwiftMap 小地图」区块，显示本维度容器数、格式版本、产出者
- 存档没有 SwiftMap 数据时，这块完全不显示（不影响原有流程）

### 验证

`crates/core/examples/verify_swiftmap.rs` 按规范手工构造一个 `.smr` 容器，
再用读取器读回，逐项比对：

```
[容器] slotCount=64 有数据槽位=1
       代际 A=2 B=1（A 更大 → 用 A 的索引）
[瓦片] 调色板 3 色，高度段 true
       像素 (0,0)   = [255,156,46] ✅（橙色）
       像素 (63,0)  = [60,184,200] ✅（青色）
       高度 (0,0)   = 64 ✅
       高度 (0,7)   = 71 ✅
       槽位 1 = 空 ✅
[按坐标查色] (10,5) / (40,5) 命中，(500,5) 无容器返回 None ✅
```

新增 6 个单元测试：容器名解析、瓦片网格数学（含负数象限）、

## 第十四轮：导入导出 SwiftMap `.smclip` 格式（2026-10-31）

参考 `D:\工程-迅捷地图\src\client\java\com\heishandashu\swiftmap\clip\` 实现。

### 格式

SwiftMap 的区块剪贴板格式（`.smclip`），魔数 `SMCP`，当前版本 **2**。

**文件结构**
```
[4]   magic "SMCP"
[2]   formatVersion      [4] dataVersion
[UTF] modVersion         [8] createdMillis
[UTF] note / sourceWorld / dimension
[4]   originChunkX/Z     [2] sizeX / sizeZ / minY / maxY
[1]   flags              [4×2] 方块调色板 + 群系调色板（UTF 数组）
-- 之后 sizeX*sizeZ 个区块载荷 --
[4] rawLen  [4] compressedLen  [N] Deflate 压缩载荷
```

`UTF` 是 Java 的 `writeUTF`：**2 字节长度 + Modified UTF-8**
（`U+0000` 编成 `C0 80`；补充平面字符拆成代理对各 3 字节）。

**单个区块载荷**
```
[2] sectionCount   [2] sectionBaseY
每段：[1] kind(0=全空气/1=有方块)
      kind==1: [1] blockBits + 位打包 4096 个索引
      若含群系: [1] biomeBits + 位打包 64 个索引
[4] 方块实体数 + NBT×N
[4] 实体数     + NBT×N
```

位打包是 SwiftMap 自己的 `PackedArray`：**低位在前、跨字节连续、无对齐要求**
（与 Minecraft 存档的"不跨 long 边界"打包不同，两套都要实现）。

### 关键差异：两套位打包

| 用途 | 规则 |
|---|---|
| Minecraft 存档 `block_states.data` | **不跨 long 边界**，`64/bits` 个/long，最少 4 位 |
| SwiftMap `.smclip` 载荷 | **跨字节连续**，低位在前，无对齐要求 |

`crates/core/src/smclip.rs` 里两套都实现了：
`pack`/`unpack`（SwiftMap 式）与 `pack_block_states`/`unpack_block_states`（存档式）。

### 高度处理

按用户要求：

- **导出：一律全部高度**（Y -64..319），不跟随当前渲染层
- **导入：不改高度**。SwiftMap 的文件可能只存了某一段高度，
  导入后按它自带的 `minY..maxY` 还原到对应 Y 位置，直接替换

### UI

工具栏的「另存区域」改为 **「导出区域」下拉菜单**：

- `Litematica (.litematic)` — 只存非空气方块
- `SwiftMap 剪贴板 (.smclip)` — 完整快照，含空气/群系/实体，最多 7×7 区块

「导入区域」按扩展名自动分派：`.smclip` 走 SwiftMap 解析器并填进剪贴板，
之后可正常「粘贴区域」；其他扩展名提示暂未实现。

### 验证

**逐方块严格比对**（不是抽样）：

## 第十五轮：修复 exe 图标不生效（2026-10-31）

### 现象

标题栏图标是对的（来自 `window_icon()` 内嵌的 RGBA），
但**资源管理器 / 任务栏看到的仍是 Windows 默认空白程序图标**。

`SHGetFileInfo` 返回的确实是默认图标，说明系统根本没读到我们的 `.rsrc`。

### 根因：三个叠加的 bug

#### 1. COFF 符号表 aux 记录多写了 1 字节

`IMAGE_SYMBOL` 是 18 字节，其后 aux 记录也必须是 18 字节。
旧代码按 `4+2+2+4+2+1+1+1(padding)+1+1 = 19` 写，**多了 1 字节**，
导致后面整个文件左移 1 字节 —— 包括字符串表长度和 `.rsrc` 数据本身。

后果：`.rsrc` 的目录头 `NumberOfIdEntries` 本该是 `2`，实际读成 `0x0200 = 512`，
资源树直接解析成垃圾。

`SectionHeader.PointerToRawData` 也指向了偏移 1 字节的位置。

**修复**：aux 记录精确写成 `4+2+2+4+2+1+1+2(padding) = 18` 字节。

#### 2. 资源类型 ID 混进了标志位

`WriteDirEntry(w, id, flag, offset)` 把 `flag | id` 写进 `Name` 字段。
`0x8000 | 3 = 0x8003 = 32771`，于是：

- `RT_ICON` 的 ID 变成 **32771**（应为 3）
- `RT_GROUP_ICON` 的 ID 变成 **32782**（应为 14）

Windows 不认识这些类型，自然不显示图标。

**修复**：`Name` 只写纯 ID；拆成 `WriteSubdirEntry` / `WriteDataEntry` 两个函数，
语义清晰不会混淆。

#### 3. 子目录标志用了 `0x8000` 而不是 `0x80000000`

`IMAGE_RESOURCE_DIRECTORY_ENTRY.OffsetToData` 的 bit31 才表示"指向子目录"，
`0x8000` 只影响低 16 位，Windows 会把它当成一个普通 RVA 去寻址，找不到数据。

**修复**：`0x80000000`（`int.MinValue`）。

#### 4. 数据项的 OffsetToData 是节内偏移，不是全局 RVA

PE 规范要求这里填**相对镜像基址的 RVA**。COFF 对象在汇编时不知道自己会被
放到哪个虚拟地址，所以只能写节内偏移（448、824…），链接器不会自动修正
（除非用重定位）。

**修复尝试**：给这 4 字节加 `IMAGE_REL_AMD64_ADDR32NB` 重定位。
**结果**：本机 lld 处理手写的最小 COFF 时直接崩溃（`0xC0000005` 访问违例），
无论带不带符号表都一样。

**最终方案**：链接后修补。`.build/patch_rsrc_rva.js` 解析 PE 节表拿到 `.rsrc`
的真实 VA，然后遍历资源树（**带严格校验**：条目数 > 64、越界、大小异常都立即中止，
避免把非资源数据当目录项改坏），把 8 个数据项的节内偏移加上 `.rsrc` VA。

已接入 `build.cmd`，每次构建自动执行。

### 教训

**"二进制结构看起来对"不等于"操作系统认"**。
这一轮每一步都用二进制 dump 验证了结构，但直到用 `SHGetFileInfo`
（系统真实读取路径）才知道前面全白费。
以后遇到这类问题，应该**一开始就用系统 API 验证**，而不是只看字节布局。

### 验证

```
ICO 源文件      : 7 个尺寸全有效，32bpp PNG 压缩
obj .rsrc       : 16160 字节（= 100 头部 + 16060 数据），Named=0 Id=2 Name=3/14
exe .rsrc       : VA=0x67B000 raw=0x675A00，8 个数据项全部修补为全局 RVA
SHGetFileInfo   : 返回草方块图标 ✅
从 exe 提取 256px: PNG magic 正确，目视为草方块 + 橙色选框 ✅
```

### 工具

- `.build/make_rsrc_obj.cs` — 生成带 `.rsrc` 的 COFF 对象
- `.build/patch_rsrc_rva.js` — 链接后修补数据项 RVA（带严格校验与 dry-run）
- `.build/icon_gen.cs` — 1024×1024 矢量绘制源图

把它和左侧按钮组分开推到右边。

> 一开始误放到了地图工具栏（「回到玩家」那一行），
> 按用户指正移到了上方主工具栏。

### 3. 关于窗口

点击后弹出居中窗口，内容：

| 项目 | 值 |
|---|---|
| 名称 | Minecraft 存档管理器 |
| 版本 | v1.0.1（正式版） |
| 作者 | 黑山大叔 |
| 主页 | https://space.bilibili.com/19428259 |
| GitHub | https://github.com/heiheids |

主页和 GitHub 用 `ui.hyperlink_to` 做成可点击链接，
底部还有「打开主页」「打开 GitHub」两个按钮，
通过 `ctx.open_url()` 交给系统浏览器。

窗口右上角的 × 和底部「关闭」按钮都能关闭，
状态用 `App::show_about` 管理，标题栏关闭时会同步回状态。
